## Map MVP Scope Summary

The MVP map scope is a Georgia-only trip map for saving places, assigning them to trip days, viewing all saved coordinate-backed places, and viewing a selected day as numbered red route points connected by a planning line. Points saved without a day remain visible as neutral gray pins when they have coordinates and remain available in lists when they do not.

The offline MVP target is a previously downloaded map area for Georgia, preferably the whole country. This is a product target, not a proven provider capability. If whole-country Georgia is not practical because of pack size, provider terms, offline limits, or device storage, any fallback to regions or cities requires owner approval.

The app should reduce the need to leave for external maps during travel by showing saved points, downloaded map context, and planned day order in-app. Yandex Maps handoff remains a fallback for point-level navigation when the app cannot provide enough navigation support. The MVP must not promise offline search, offline geocoding, offline routing, turn-by-turn navigation, traffic, route optimization, live rerouting, or provider-native/offline readiness until separately proven and accepted.

## Explicit In-Scope Capabilities

### Geography

- Georgia is the only MVP country.
- The first offline target is a whole-country Georgia map downloaded before travel.
- A smaller Georgia region/city fallback is allowed only after owner approval.

### Online Map And Search

- Open the map, zoom, and pan.
- Search online for concrete places, landmarks, or addresses, such as Narikala Fortress or Ali and Nino.
- Show search suggestions/autocomplete only if the selected production provider allows that usage under acceptable terms, limits, pricing, and key model.
- Add a search result as a trip point.
- Add a point by tapping/clicking the map.
- Add a place manually by text when search is unavailable, has no result, or the user is offline.
- Save a point with `no day` or with one trip day assignment.
- Change day assignment later.
- Show user-visible states for no network, no results, provider failure, no coordinate, and outside downloaded area.

### Saved Points And Lists

- A saved point may have title, optional address, optional note/comment, coordinates when known, day assignment, source, and later timestamps when persistence exists.
- Coordinate-backed no-day points appear on the map as neutral gray pins.
- Coordinate-backed day-assigned points appear as route/day points, preferably red.
- Points without coordinates stay saved and readable in lists/day plans, but do not render as pins.
- Saved lists/details remain the source of truth when map display, search, or external navigation fails.

### Day Route Display And Ordering

- The map supports all-points view, no-day points view, and selected-day view.
- When a day is selected, the map shows that day's route points as numbered red pins.
- The selected day's points are connected by a route/order line.
- The line is a planning/order visualization, not turn-by-turn navigation and not proof of road-snapped routing.
- Route order is edited through place cards below the map.
- Reordering place cards updates point numbering and redraws the route/order line.
- Dragging map pins to reorder the route is outside the MVP editing model.

### Offline Map Viewing

- User can see whether the trip map area is not downloaded, downloading, downloaded, or failed.
- User can trigger the Georgia map download before travel once provider support is proven.
- A previously downloaded map area opens without network once implementation proof exists.
- Saved coordinate-backed points render over the downloaded map.
- Saved day route/order renders over the downloaded map as a visual planning line.
- Zoom and pan work inside the downloaded area.
- Saved lists/details remain readable even when offline map tiles are missing or the user is outside the downloaded area.
- UI copy must distinguish offline map viewing from offline routing/navigation.

### External Map Fallback

- A saved point or address can be opened in Yandex Maps when coordinates or address are sufficient and the device supports handoff.
- If handoff cannot open or target data is insufficient, the app preserves the saved address/coordinates and shows a clear unavailable state.
- External maps are a fallback, not the primary route planning experience.

## Explicit Out-Of-Scope Capabilities

- Any MVP country beyond Georgia.
- Worldwide offline map packs.
- Automatic offline area selection for arbitrary countries.
- Multi-country offline trips.
- Offline place search.
- Offline geocoding.
- Offline turn-by-turn navigation.
- Offline route optimization.
- Offline routing unless a provider later proves it and the owner explicitly accepts a scope increase.
- Road-snapped native route calculation as an MVP commitment.
- Live traffic, travel-time estimation, live rerouting, or disruption support.
- Automatic route optimization in online or offline mode.
- Map pin dragging as the route-order editing mechanism.
- Category discovery or recommendation browsing, such as generic nearby cafe discovery, if it delays concrete-place search.
- Public Nominatim autocomplete in prototype or production.
- Treating deliberate low-volume public Nominatim prototype search as production-provider proof.
- Making Yandex Maps or any external map the primary map experience.
- Storing provider-specific raw responses in domain models unless separately approved by architecture/security/provider terms.
- Promising native iOS/Android SDK behavior, offline tile download, offline reopen, or app restart persistence based on the current web prototype alone.

## Provider-Proof Blockers

The following items block production map implementation or broad MVP promises until proven and reviewed:

- Native MapLibre React Native development build proof for iOS.
- Native MapLibre React Native development build proof for Android, or a documented blocker.
- MapLibre map rendering inside a development build; Expo Go is not enough.
- User-triggered bounded offline pack download with visible progress and error states.
- `OfflineManager.getPacks` or equivalent pack inventory surviving app restart.
- Network-disabled app reopen rendering the downloaded area.
- Saved trip points rendering over the offline map.
- Pack delete/cleanup behavior.
- Measured pack size and download duration for a representative Georgia area.
- Evidence whether whole-country Georgia can fit provider terms, provider limits, device storage, and acceptable download time.
- Tile/style provider selection and approval, including terms, pricing, offline/cache limits, attribution, and API key model.
- Stadia Maps is constrained by the reported 100 MB per-device offline cache ceiling and needs owner acceptance if used.
- MapTiler remains blocked until prepared-area download is confirmed as allowed by the selected plan/agreement.
- Search/geocoding provider selection, with accepted terms for query usage, rate limits, attribution, API key model, and storage of selected geocoding results.
- Autocomplete/suggestions proof from a production provider; without it, search should remain explicit user-triggered search plus manual fallback.
- Security/privacy guardrails for mobile API keys, provider data sharing, logging, and offline attribution.
- Test fixtures for no network, provider timeout/failure, no results, missing coordinates, linking failure, and outside downloaded area.

## Owner-Facing Open Questions

1. If whole-country Georgia is too large or not allowed by provider terms, which Georgia fallback areas should be approved first: regions, cities, or one manually chosen area per trip?
2. What is the maximum acceptable offline map pack size and download time for the first MVP trip?
3. Is one downloaded area per trip acceptable for MVP?
4. Which representative Georgia area should be used for the first provider/device proof?
5. Should the offline-map preparation warning be persistent before travel until download succeeds, or shown only on the map/offline status surface?
6. Is copying an address/coordinates an accepted fallback when Yandex Maps handoff cannot open, or should the fallback only display the saved address?
7. Should online autocomplete be required for first release, or is explicit search submission acceptable if provider terms/rate limits are not yet accepted?
8. Should generic category discovery be explicitly deferred until concrete-place search and manual fallback are proven?

## Product Risks

- Users may interpret downloaded map support as offline navigation unless copy and acceptance criteria clearly say saved map viewing, saved points, and planned order only.
- Whole-country Georgia may be infeasible under provider terms, per-device offline limits, pack size, or device storage; treating it as proven would create rework and user trust risk.
- A map-led failure state could hide the reliable saved day plan and lists unless local/manual fallbacks stay primary.
- Missing-coordinate places can feel lost unless they remain visible in lists with a clear not-on-map-yet state.
- External navigation fallback can look like core functionality failure if address/coordinate requirements and handoff failures are not explained.
- Provider search or autocomplete decisions can delay MVP if manual entry and explicit search are not kept acceptable.
- API key, attribution, and provider data retention constraints can force UX or technical changes late if not reviewed before implementation.
- The web prototype may create false confidence because it does not prove native SDK behavior, offline packs, offline reopen, or persistence after restart.
